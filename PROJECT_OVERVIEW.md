# Устройство проекта payment-courier-tool

Проект решает две связанные задачи:

1. распределяет готовые PDF-платёжки по папкам курьеров;
2. формирует новые PDF-платёжки из XML поставщика.

Документ нужен как короткая карта проекта: где находится логика, что за что отвечает
и куда смотреть при доработках.

## Поток “XML → PDF”

1. UI вызывает `ParserPresenter#createPdfFromXml`.
2. `ParserPresenter` запускает задачу через `ParserTaskRunner`, чтобы интерфейс не зависал.
3. `XmlPaymentPdfGenerationService` находит XML-файлы и создаёт отдельную папку результата для каждого XML.
4. `XmlPaymentDocumentParser` потоково читает XML и собирает `PaymentDocument`.
5. `XmlPaymentPdfWriter` управляет PDF-файлами: открывает документ, грузит шрифты, считает страницы и сохраняет результат.
6. `XmlPaymentPdfPageRenderer` рисует одну страницу платёжки.
7. Результат сохраняется как `payment-documents-001.pdf`, `payment-documents-002.pdf` и далее.

Важные детали:

- `PaymentAddressPrintFormatter` готовит адрес в шапке платёжки. Если в XML есть адрес помещения,
  печатается он; если нет — используется адрес доставки.
- `PdfQrCodeRenderer` рисует QR-коды напрямую в PDF. Это отдельная ответственность, потому что
  читаемость QR банковским приложением критична.
- `XmlPaymentPdfPageRenderer` намеренно содержит ручную PDF-вёрстку. Его нужно менять осторожно:
  размеры шрифтов, высота строк и границы таблиц сильно влияют на визуальное совпадение с образцом.

## Поток “PDF → курьеры”

1. UI вызывает `ParserPresenter#createCourierPdfs`.
2. `CourierPaymentService` читает адреса курьеров из папок.
3. Для каждой страницы PDF извлекается текст через PDFBox.
4. `AddressExtractor` достаёт адрес платёжки.
5. `CourierMatcher` нормализует адрес дома и ищет подходящего курьера.
6. `PdfPageTempStorage` временно сохраняет страницы.
7. `CourierPdfWriter` собирает итоговые PDF по курьерам.
8. Отчётные классы из `org.vc.report` формируют итог сортировки, реестр адресов и списки проблемных адресов.

Важные детали:

- Для XML-платёжек нельзя делить документ по каждому `Лицевой счет:`: в таблице получателей их может быть несколько.
- Главный адрес платёжки ищется по `Адрес помещения:` или `Адрес доставки:`.
- Адреса поставщиков из реквизитов не должны попадать в распределение.
- Для сопоставления с курьером используется адрес дома без квартиры.

## Адресная логика

Адреса разделены на несколько уровней:

- `AddressExtractor` достаёт адрес из текста PDF.
- `AddressParser` приводит адреса из Excel к формату домов.
- `PaymentAddressParts` разбирает адрес платёжки на город, улицу, дом, корпус и квартиру.
- `AddressKeyNormalizer` строит ключ дома для сравнения адресов.
- `AddressNormalizer` выступает фасадом для общей нормализации.

При доработке адресов сначала добавляйте тест на конкретный пример, а уже потом меняйте регулярные выражения.
Так меньше риск сломать старые PDF.

## PDF-логика

В проекте есть два разных PDF-сценария:

- `CourierPdfWriter` собирает готовые страницы в PDF по курьерам.
- `XmlPaymentPdfWriter` управляет пачкой PDF-файлов из XML.
- `XmlPaymentPdfPageRenderer` рисует страницу новой платёжки из XML-данных.
- `PaymentAddressPrintFormatter` выбирает и чистит адрес для шапки платёжки.
- `PdfQrCodeRenderer` рисует QR-код оплаты.
- `PdfFontLoader` находит системные шрифты Windows для PDFBox.

После изменений PDF-вёрстки нужно руками проверить минимум:

- маленькую платёжку;
- большую платёжку с несколькими получателями;
- платёжку с несколькими приборами учёта;
- платёжку с двумя QR-кодами.

## UI и MVP

UI построен по близкой к MVP схеме:

- `ParserFrame` — Swing-представление.
- `ParserView` — контракт представления.
- `ParserPresenter` — пользовательские сценарии и валидация выбранных путей.
- `ParserTaskRunner` — запуск задач в фоне и защита от повторного старта.

Для этого проекта полноценная многослойная архитектура была бы тяжелее, чем нужно.
Пакетного разделения достаточно: приложение небольшое, но сценарии уже разные.

## Почему проект не разбит на Maven-модули

Сейчас один Maven-модуль — нормальный баланс. Код уже разделён по пакетам, а Maven multi-module
добавил бы больше сборочной сложности, чем пользы.

Если проект вырастет, первым кандидатом на отдельный модуль будет домен + XML/PDF-генерация,
но сейчас это преждевременно.

## Проверка после изменений

Минимальный безопасный набор:

```cmd
mvn test
mvn -DskipTests package
```

После изменения PDF-вёрстки дополнительно нужно открыть контрольные PDF и проверить:

- текст не налезает на таблицы;
- QR-коды читаются банковским приложением;
- платёжка остаётся на одном листе, если это возможно без полной потери читаемости;
- таблицы идут в том же порядке и с теми же смысловыми блоками, что в образце.

## Правила доработок

- Не менять формат адресов без теста на конкретный пример.
- Не использовать адреса поставщиков как адреса помещения.
- Не трогать размеры таблиц в `XmlPaymentPdfPageRenderer` без визуальной проверки.
- Не запускать параллельно две генерации в одну папку результата.
- Не добавлять JavaDoc вида “параметр” или “возвращает значение”: лучше без комментария, чем с шумом.
